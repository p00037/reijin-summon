# ルーム制オンライン対戦の設計案

作成日: 2026-09-21
状態: 2026-09-21にユーザーが承認済み。実装計画を作成済み、計画レビュー待ち。実装未着手。

実装計画: [オンライン対戦実装計画](../plans/2026-09-21-online-battle.md)。

## 1. 目的と確定要件

知人とルーム番号を共有し、既存カードと召喚獣で1対1の対戦を最後まで遊べるようにする。

- ローカルで検証してからインターネット公開する。
- ログイン不要。表示名とルーム番号で参加する。
- 通信切断中も試合は進行し、30秒以内は復帰可能。期限を過ぎると切断側の敗北。
- 相手のデッキと初期配置は戦闘開始時に公開する。
- タブレットを優先し、既存のタッチ・複数指操作を維持する。
- 公開費用は無料。接続規模は最大10人を想定する。
- 固有スキル完成やCPU強化を対人戦の前提としない。

最大10人は、対戦・待機・再接続用に確保した席を含む10席と解釈する。1試合2席、同時5試合を検証対象とする。以下の細部はこの設計案で提案する。

## 2. 方式の比較と選択

| 方式 | 利点 | 今回の判断 |
| --- | --- | --- |
| 既存Colyseusサーバーで戦闘を実行する | 既存資産を使え、双方の勝敗・状態を統一できる | 採用案 |
| 片方のブラウザを対戦の管理役にする | サーバーの戦闘計算を減らせる | 管理役の切断や不正操作に弱く、採用しない |
| 別の通信基盤へ作り替える | 公開先に合わせた構成にできる | 移行範囲が大きいため初回は採用しない |

戦闘処理は共有パッケージに移し、CPU戦はブラウザ、対人戦はサーバーで実行する。描画とタッチ入力はクライアントに残す。

## 3. 初回の範囲

- 既存20枚、デッキの1〜5枚・コスト10以下・同カード重複禁止、既存6種類の召喚獣を使用する。
- 兵種共通アビリティ、召喚、復活、エレメンタル、300カウントの勝敗ルールを両者に適用する。
- CPU戦を維持する。CPUの戦術・能力使用判断の強化は別作業とする。
- ランク、公開ルーム一覧、自動マッチング、観戦、チャット、戦績保存、リプレイ、固有スキルは含めない。
- デッキ保存は現在のブラウザ内保存を維持する。

## 4. 画面と対戦の流れ

1. タイトルからCPU戦またはオンライン対戦を選ぶ。
2. オンラインでは表示名を入力し、ルーム作成または番号で参加する。
3. 作成者に重複しない6桁のルーム番号を表示する。1ルーム2人まで、途中の第三者参加は禁止する。
4. 待機画面には名前と準備状況を表示する。各自が保存デッキと召喚獣を選ぶ。
5. 自軍の初期配置を調整して準備完了する。準備完了後は編成・配置を固定する。相手の準備完了前なら解除できる。
6. 双方が接続中かつ準備完了した時点で5秒のカウントダウンを開始する。相手情報はまだ送らない。
7. カウントダウン終了時に相手情報を送信し、戦闘を開始する。
8. 終了時に両者へ同一の結果と終了理由を通知する。双方が再戦を選べば同じルームで編成・配置へ戻る。片方が退出したら部屋を閉じる。

表示名は前後空白を除いた1〜20文字の文字列とし、制御文字を拒否する。HTMLとして挿入しない。ルーム番号は本人確認情報ではない。再接続の本人確認には別の秘密トークンを使う。

## 5. 共有ルールと両陣営対応

- `src/shared` をnpm workspaceとして追加し、型、数値設定、カード・召喚獣定義、デッキ検証、戦闘ルールを集約する。Phaser・DOM・ブラウザ保存への依存を持たせない。
- 既存の `Player` / `Cpu` は当面内部の陣営識別値として維持する。オンライン画面では自分・相手として扱う。
- 初期配置、能力AP回復・使用、復活、召喚、向きの扱いを両陣営に対応させる。
- サーバーが接続と陣営を結び付ける。クライアントが申告した陣営や能力値は信用しない。
- キーパー能力など方向依存の判定は、サーバー座標の有限な向き入力と陣営に基づいて両側で同じ条件を適用する。表示用の向き変換とは分離する。
- CPU戦の開始処理とオンラインの双方準備完了処理は別の進行管理に置き、戦闘計算を共通利用する。
- Node.jsで共有パッケージを読み込める出力・import形式に統一し、共有→サーバー／クライアントの順でビルドする。

## 6. 同期と入力

- サーバーだけが時間、移動、攻撃、HP、MP、AP、召喚ゲージ、勝敗を更新する。
- 初期値として戦闘更新20回/秒、状態配信10回/秒を採用する。位置はクライアントで補間する。負荷測定により変更する場合は検証結果を記録する。
- クライアントは操作種別、ユニットID、必要な座標・向き、試合ID、連番を送る。古い試合・重複連番・権限外・無効なフェーズの操作は拒否する。
- 移動指示は既存のドラッグ確定時に送る。ドラッグ中のプレビューと指への追従は端末内で即時描画する。
- 状態通知には試合IDと更新番号を付け、古い状態で巻き戻さない。再接続時は完全な状態を送る。
- 戦闘状態はColyseusのスキーマで同期し、開始前のデッキ・配置はルーム内の非公開データとして保持する。準備中は各本人にだけ必要な情報を送る。画面で隠すだけの実装にしない。
- 攻撃・召喚演出にはイベント番号を付ける。配信間に発生したイベントを落とさず、再接続時に過去の演出を再生しない。
- 双方が自軍を手前に見る。後参加側は座標と向きを180度変換し、入力では逆変換する。ユニットIDは変更しない。HP・MP・勝敗表示も自分基準に変換する。
- 再接続中は操作を無効化し、未送信・未確認の古い操作を復帰後に再送しない。
- プロトコル版を接続時に照合し、公開更新後に古い画面で接続した場合は再読み込みを案内する。

## 7. 切断・退出・終了

- 切断検出はサーバー側で行い、検出から30秒の猶予を計測する。タブレットのスリープ・タブ切り替えでも同じ扱いとする。
- 試合中は最後の移動指示と自動戦闘を続ける。CPUによる代理操作はしない。
- 準備中の切断では開始を止める。カウントダウン中なら準備画面に戻して双方の準備完了を解除する。
- 再接続情報は同じタブの `sessionStorage` に保持する。同じブラウザ・タブの再読み込みから復帰可能とし、別端末への移行は対象外とする。
- 片側だけが切断し期限切れになった場合、試合中なら敗北、開始前なら部屋を閉じる。
- 両者不在の場合、両者の猶予が切れるまで待ち、復帰がなければ勝敗なしで閉じる。片方だけ復帰し、相手の猶予がすでに切れていれば復帰者の勝利とする。
- 切断猶予中に通常の勝敗が成立した場合はその結果を優先する。結果は一度だけ確定する。
- 明示的な試合中の退出は降参として扱い、誤タップ防止の確認を表示する。
- サーバー再起動・停止で状態が失われた場合は勝敗なしの中断と表示する。30秒再接続は生存中の同じサーバーに対する復帰であり、サーバー障害からの試合復元は初回の対象外とする。
- 1人で待機する部屋は10分、準備画面は最終操作から10分、結果画面は2分で閉じ、席を解放する。無操作による終了には画面で予告を出す。

## 8. 定員とサーバー側の検証

- 1プロセスで動かし、接続・復帰予約を含む最大10席を管理する。満員時は新規参加を拒否し、予約済みの復帰は許可する。
- デッキ、召喚獣、入力構造、有限座標、配置範囲、ユニット所有権、各操作条件をサーバーで検証する。
- コマンドは1接続あたり毎秒30件まで、メッセージは8KiBまで。超過は拒否し、継続的な超過は切断する。
- 作成・参加要求はIPあたり毎分30回を初期上限とする。同一Wi-Fiの10人で参加できることを検証する。転送元IPは公開先のプロキシ設定に合わせて扱う。
- 公開時はHTTPの許可元とWebSocket接続のOriginを設定する。これらは本人確認の代わりにはしない。
- 再接続トークンはログや他プレイヤーへの通知に含めない。

## 9. タブレット対応と検証

- 横向きのタブレットを基本レイアウトとし、縦向きでも操作領域を欠けさせず、必要なら横向きの案内を出す。
- 主要ボタンは44 CSS px以上を目安とし、ホバーや右クリックを必須にしない。
- ゲーム操作領域だけでブラウザのスクロール・ズームとの競合を抑え、表示名入力は通常の入力欄で行う。
- 複数指の移動指示、復活ドラッグ、アビリティ、召喚、指が領域外へ出た場合、画面回転、復帰時の指状態リセットを検証する。
- iPadOS SafariとAndroid Chromeのタブレットを検証対象とする。実機が利用できなければ、エミュレーション済みと実機未確認を区別して報告する。
- PCブラウザでも既存のマウス操作を維持する。

## 10. 無料公開の構成と変更点

構成案は、クライアントを既存のCloudflare Pages向け構成で配信し、Node.js／ColyseusをRenderのFree Web Service 1台で動かす。データベースは追加しない。Renderアカウントや公開リソースはこの設計段階では作成しない。

| 項目 | ローカル検証 | 公開時 |
| --- | --- | --- |
| 接続先 | PC上のサーバー。タブレットからはPCのLANアドレス | `VITE_GAME_SERVER_URL` を公開サーバーURLに変更しクライアントを再ビルド |
| 通信 | HTTP／WS、または検証環境に応じたHTTPS／WSS | HTTPS／WSSを使用 |
| 許可元 | ローカル・LAN上のクライアントURL | 本番クライアントのOriginを `ALLOWED_ORIGINS` に設定 |
| 起動 | 開発用プロセス | 共有コードとサーバーをビルドして本番起動。ホストの `PORT` を使う |
| 外部接続 | 同一Wi-FiからPCに接続可能な待受・必要なファイアウォール設定 | ホストの公開URL・TLS・ヘルスチェックを設定 |
| 運用 | 開発者が起動 | 起動待ち表示、容量・通信量確認、試合のない時間帯の更新 |

上記の環境変数と公開用ビルド手順を実装時に用意し、公開のために戦闘ルールを書き換えない。独自ドメインは不要。実際の公開URLを取得してから設定値を埋める。

2026-09-21確認時点で、Render無料枠には15分の無通信での休止、再起動時の約1分の待ち、月750時間の共有枠、転送量・ビルド枠の制限、任意の再起動がある。無料枠超過時の追加課金を避ける設定を公開前に確認し、上限で利用停止となる運用を受け入れる。無期限の無料・常時稼働は保証しない。

WebSocketに接続数の固定上限はないが、計算資源と転送量には制約がある。10人で十分かは未測定のため、5試合の負荷試験と転送量測定で判断する。休止を避けるためだけの常時アクセスは設けない。

出典: [Render無料枠](https://render.com/docs/free)、[Render WebSocket](https://render.com/docs/websocket)。公開直前に条件を再確認する。

## 11. 完了条件と実施順

### 第1段階: 戦闘ルールの共通化

- 共有ルールをブラウザとNode.jsの双方でビルド・実行できる。
- 両陣営の配置、AP、能力、召喚、復活の対称性をテストする。
- CPU戦の既存テスト、型検査、ビルドが通る。既存の操作から結果画面までの動作を確認する。

### 第2段階: ルームと準備

- 2クライアントで作成・参加・編成・配置・準備完了ができる。
- 満員、不正デッキ、重複番号、開始後参加を扱える。
- 開始前に相手情報がネットワーク上に流れないことをテストする。

### 第3段階: 同期・切断とローカル完走

- 両者が逆側の陣営を操作しても同じルールで300カウントの試合が完了し、勝敗が一致する。
- 通常撃破、時間切れ、引き分け、降参、切断29秒以内の復帰、30秒期限切れ、両者切断、サーバー停止を確認する。
- 無効入力でサーバーが停止しない。他人のユニット操作や古い操作を拒否する。
- タブレットの複数指操作・再読み込み・回転を確認する。
- 5試合同時に10分以上動かし、戦闘更新の95パーセンタイルが50ms未満で、処理の遅れが蓄積せず、試合結果が一致することを測定する。メモリ・転送量も記録する。

### 第4段階: 公開検証と追加開発

- 無料枠・課金設定・接続先を確認して公開する。
- 別ネットワークの端末で接続、1試合、再接続、休止後の起動待ちを確認する。ローカルの性能測定だけで公開先の性能を保証しない。
- 固有スキルとバランス調整は、この対人基盤で遊べる状態になってから別の仕様として進める。

設計書の確認後、変更箇所と検証を分割した実装計画を作成し、ユーザー指定がなければ現在のタスク内で順次実装する。
